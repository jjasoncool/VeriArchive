# Registration and relocation write chunk lines, the index holds them, and a FULL verify compares them

Decision 0031 built the pieces of chunk lines: the Merkle tree, the chunk hashes in the read pass, and the writer and strict reader of chunk lines. Registration and relocation still wrote chunk size 0, and the index kept no chunk hashes: `chunks` stayed empty and `archive_revisions.merkle_root` NULL, as V1 left them. This stage switches them on, and verifies by them. The operator decided (2026-10-16) that new archives, and new revisions of archives registered by V1, use 64 MiB chunks, and that an archive that has a chunk size keeps it; that an archive registered by V1 otherwise gets chunk hashes only through a FULL verify that adds them, which records a new revision only when every file matched; that a FULL verify that finds a large file's content changed names which chunks differ, as in "content differs: chunks 3 and 17 of 160 differ, the first from byte 201,326,592"; that a file whose content matches both its file hashes while one of its chunk hashes does not gives `PASSED_WITH_WARNINGS`, with a warning that this file's chunk hashes cannot be relied on and that a new revision fixes them (the manifest was wrong when written, the file is fine); and that QUICK and DEEP, which need chunk hashes, come in a later stage, as does the FULL verify that adds chunk hashes. This record states what registration, relocation, import, export, rebuild-index, a FULL verify and the interface now do, with the technical details decided for them.

## Decision

1. **The chunk size of a revision.** Registration fixes it when it makes its plan: 64 MiB (67108864) for a new archive, also one registered with `--force-new-archive`; for a new revision, the chunk size of the archive's latest revision as its manifest says (never the index's copy of the header, R-14), and 64 MiB where that is 0, as it is for every revision V1 wrote. So an archive keeps its chunk size, and one registered by V1 gets 64 MiB at its next registration. A relocation keeps the chunk size of the revision rN it verifies, also 0 (point 5). Import and rebuild-index index a manifest as its header says.

2. **The plan holds it.** A registration's plan (`registration:<archive_uuid>`, decision 0022) gains the member `chunk_size`, written when the plan is made. Every attempt of the registration hashes, saves and records at it, whatever chunk size a resume is given. A plan without it was written before this decision, by attempts that saved their files without chunk hashes: its registration finishes at chunk size 0, so that no saved file is read again, and the archive's next registration takes 64 MiB. A `chunk_size` that is no chunk size, which no version writes, counts as none.

3. **The index.** The schema version is 2. Version 1, V1's, created every table of §B8, `chunks` and `archive_revisions.merkle_root` among them, and left those two empty; version 2 fills them and adds no table or column (R-92):
   - `chunks` holds one row per chunk line of a recorded revision, keyed as the file's row in `files` (decision 0002; `stream` is `''`, as only files have chunk lines), with `idx`, `offset`, `length` and `b3`; `last_verified_at` stays NULL until QUICK and DEEP use it.
   - `archive_revisions.merkle_root` is the revision's Merkle root as its header gives it: `merkle_root` where the chunk size is not 0, NULL otherwise, as a reader then ignores `merkle_root` (decision 0031).
   - A file's chunk rows are written with its row, and only all of them: the chunk hashes of exactly the files that have chunk lines at the chunk size given (decision 0031, point 2), or nothing is written. Whatever removes a file's row removes its chunk rows: a resume that does not reuse a saved file, abandoning a registration (decision 0025), an import over rows that no plan names (decision 0030), a registration's record, which replaces its saved progress with the index, and `repo rebuild-index`. A file whose chunk rows do not run from `idx` 0 without a gap is read back without chunk hashes.
   - **Upgrading.** The first time this version opens a repository of schema version 1, it raises the version to 2 in one write transaction, so that a crash leaves 1 or 2. It reads the version first without the write lock, so that a repository at version 2 opens while another process holds that lock. An open that finds an older version waits for the lock while another process holds it, as an open of the same repository in another process does while it copies the database to upgrade it (below): each try waits as long as a statement does (5 seconds, `busy_timeout`), and between tries the open reads the version again. Once another process has upgraded the database, the open opens it without upgrading it, keeping no copy and saying nothing of an upgrade, however long the lock stays taken; otherwise it tries again for up to 2 minutes, as the record of an operation waits for the lock (`record_lock_wait`, decision 0023), and then fails (exit 11) with SQLite's cause, "cannot upgrade the repository database to schema version 3: cannot execute SQL: database is locked", having changed nothing. From then on a V1 program refuses the repository ("unsupported repository schema", exit 11): it neither writes nor removes chunk rows, so that its abandoning and its rebuild-index would leave chunk rows of files that are gone, its import and rebuild-index would record no Merkle root, and its relocation of a revision with chunk lines writes one that V1.1 rejects (decision 0031). Decision 0031 advised that only V1.1 operate an upgraded repository; the version now makes it so. A repository at a version this program does not know is refused, as before.
   - **A copy before the upgrade** (operator, 2026-10-17). The transaction that upgrades a database of an older schema version (1, or 2 since decision 0033) first keeps a copy of it as it is, beside it in RepositoryRoot, named so that anyone sees what it is, by the version it has and the day: `veriarchive-schema-1-before-upgrade-2026-10-17.db`, the date as the computer's clock shows it (decision 0017). The copy is made once the transaction holds the write lock and before it changes anything, through SQLite's backup API from a read-only connection of its own (the backup API reads no connection that is in a write transaction): it is the very database upgraded, whole and consistent, at the version it had, with every row of the verification history. It is written as `<name>.partial`, synced by its own commit (`synchronous=FULL`), and then renamed, so that a copy cut short by a crash never has the name of a whole one. A file of the name is never replaced: the copy takes `-2`, `-3`, ... before `.db`, as when a copy put back is upgraded again on the same day; a leftover `<name>.partial`, which only an attempt that holds the write lock writes, is replaced. When the copy cannot be made, nothing is upgraded or changed: the open fails (exit 11) with "cannot keep a copy of the repository database at P before upgrading it from schema version 1 to 3, so the repository was not upgraded: C" (SQLite's cause, as "database or disk is full"). An upgrade that fails after its copy removes the copy, which would be of a database that was not upgraded. The open that upgraded the database says once where the copy is: the CLI on stderr, also with `--json`, "note: the repository database was upgraded from schema version 1 to 3, which earlier versions of VeriArchive cannot open; a copy of it from before the upgrade is kept at P"; the GUI in Settings, where it opens the repository ("Note: ..."), which the window then shows first. Nothing reads the copies, and they stay until the operator removes them.

4. **Saved progress (R-104).** A registration saves each file it hashed with its chunk hashes, in the transaction and behind the guard that save the file's row (its revision not recorded, its plan still the registration's own: decisions 0023, 0025). A resume reuses a saved file only when it is unchanged (size and mtime, as before) and has all its chunk hashes at the plan's chunk size; one whose chunk rows are incomplete is read again, and its rows are replaced, as those of a file that changed. The record writes the manifest at the plan's chunk size and, in the transaction that names it (decision 0023), the chunk rows and the Merkle root.

5. **Relocation** (decisions 0004, 0026) writes r(N+1) at rN's chunk size. Every file that matched, also one matched by an attempt before a resume, carries rN's chunk hashes, as it carries rN's file hashes; an entry unreadable at registration has none (decision 0010). The writer computes the Merkle root again from what it writes: rN's, except where a driver translated a link's absolute target (decision 0008), which r(N+1) records with the new carrier's target, whose hash is a leaf. A revision without a chunk size is relocated without one: a relocation compares whole files, and gives an archive no chunk hashes (point 6).

6. **Archives registered by V1** keep their revisions as they are: chunk size 0, no chunk rows, no Merkle root. They get chunk hashes at their next registration (point 1), or through a FULL verify that adds them, of a later stage.

7. **Import, export, rebuild-index and comparison.** An import indexes the chunk rows and the Merkle root of the manifest it validated (decision 0030). An export copies the manifest with its chunk lines, as before. `repo rebuild-index` rebuilds `chunks` and `merkle_root` with the rest of the index from the manifests it reads, and keeps the chunk rows of a registration's saved progress with its rows of `files` (decision 0026). A comparison (decision 0020) compares entries by their whole-file hashes and never by chunks: an original registered without chunk lines (by V1) and a copy registered with them are `IDENTICAL` when their content is.

8. **What is shown.** `archive show <uuid>` gives each revision's chunk size, number of chunks and Merkle root, read from the revision's manifest as the latest revision's header is (`load_recorded_header`), never from the index. With `--json`, each member of `revisions` gains `chunk_size`, `chunks` (the header's `counts.chunks`: the chunks of the files larger than the chunk size, which have chunk lines) and `merkle_root` (null without a chunk size). Without it, a line under each revision says "chunk size 64 MiB, 160 chunks, Merkle root <64 hex digits>", or "chunk size 0: whole-file hashes only"; the chunk size is given in the largest unit that keeps it whole (MiB, else KiB). A revision whose manifest cannot be used stops `archive show`, as the latest revision's already did ("cannot use the manifest of revision N of archive U: ...; restore it from a backup of the repository", exit 11). `register --json` gives `counts.chunks`. The GUI shows no revision's details (the Archive List shows the number of the current revision), so it shows none of these.

9. **Tests use small chunks.** The engines take the chunk size of an archive that has none as a parameter of the registration (`RegisterRequest::chunk_size`, 64 MiB unless set): tests use 64 KiB, and 0 to register as V1 did. Relocation, import and rebuild-index take theirs from the manifests.

10. **A FULL verify compares by chunk.** The read that hashes a file whole (R-101) also hashes its chunks, at the chunk size of the revision verified (decision 0031, point 3): verifying by chunk reads nothing more, and a revision without a chunk size (0, as V1 registered) is read as before, with no chunk work. A file with chunk lines whose content differs at its recorded size, a file hash not matching, names the chunks whose hashes differ, by their `idx`, which counts from 0 as in the chunk lines, of the file's number of chunks, and the byte where the first of them begins (operator, 2026-10-16): "content differs: chunk 1 of 3 differs, from byte 67,108,864", "content differs: chunks 3 and 17 of 160 differ, the first from byte 201,326,592". Consecutive chunks are named as a run ("chunks 3-5 and 17"), at most ten runs, then "and N more" with the number of chunks left. A file whose size changed stays "size differs"; a file without chunk lines says "content differs", as before; one whose chunks all match though a file hash does not is fine (point 11). `verify --json` gives such an item `differing_chunks` (the `idx` of every chunk that differs, ascending), `chunks` (the file's number of chunks) and `first_differing_offset` (where the first of them begins); the history keeps its detail (`verify_items.detail`), which names them. The CLI's text output and the GUI's report show the detail, in English or Traditional Chinese. A relocation compares whole files (point 5): its read gives no chunk hashes and names no chunks, and r(N+1) carries rN's chunk lines as they are, which the FULL verifications of r(N+1) compare.

11. **Chunk hashes that do not match a file that matches.** A file whose content matches both its file hashes while the hash of one or more of its chunks does not is fine: its manifest was wrong when it was written (operator, 2026-10-16). It counts as `Verified` (or `MetadataMismatch`, as its metadata says), its bytes as read and matched, and the run gets a warning, which makes it `PASSED_WITH_WARNINGS` at best: "the chunk hashes of big.bin cannot be relied on: chunk 1 of 3 does not match, while the whole file matches its hashes; the file is fine, and a new revision fixes them", the chunks named as in point 10. A new revision of the archive (`register --new-revision`) reads the file again and records chunk hashes that match it. The warnings come in the canonical order of their files (R-43), whichever reader finished first.

    **The other half** (operator, 2026-10-17). A file with chunk lines whose every chunk, read by chunk, matches its recorded hash while one of its file hashes, BLAKE3 or SHA-256, or both, does not is fine as well: its chunk hashes are BLAKE3 hashes of all of its bytes, so the file hash recorded was wrong when the manifest was written. It counts as `Verified` (or `MetadataMismatch`), its bytes as read and matched, and the run gets a warning, which makes it `PASSED_WITH_WARNINGS` at best: "the whole-file BLAKE3 hash of big.bin cannot be relied on: it does not match, while each of the file's 3 chunks matches its chunk hash; the file is fine, and a new revision fixes it" ("SHA-256"; for both, "the whole-file BLAKE3 and SHA-256 hashes of big.bin cannot be relied on: they do not match, ...; the file is fine, and a new revision fixes them"). A file whose chunks do not all match stays `Modified`, naming the chunks that differ (point 10), whatever its file hashes; a file without chunk lines whose file hash does not match stays `Modified` too, as nothing else vouches for its content. A new revision records file hashes that match the file. A relocation compares whole files (point 5): there such a file differs, and the relocation refuses the new carrier until a new revision of the archive has fixed the hash.

12. **A resumed FULL verify compares by chunk (R-104).** A checkpoint (`verify_progress`) says that an entry's content matched its file hashes and, for a file with chunk lines, every chunk hash: a file whose chunk hashes did not all match is not checkpointed, nor one whose file hash did not while its chunks did. A resume compares by chunk as every FULL verify does, and reads again what is not checkpointed: a file whose content differs names its chunks again, and one whose chunk hashes or file hash cannot be relied on gives its warning again. The checkpoints of a run that an earlier version interrupted were made comparing whole files; a resume takes them as they are, as their content matched, and compares by chunk what it reads.

## Why

**64 MiB for an archive registered by V1 at its next revision.** A new revision reads the whole archive anyway, and the read that hashes a file gives its chunk hashes (R-101); waiting for a FULL verify that adds them would leave such an archive without them and save nothing.

**The chunk size fixed in the plan.** The attempts of one registration save and reuse each other's chunk hashes, which are hashes at one chunk size, and a manifest has one chunk size. Fixed when the plan is made, every attempt hashes at the chunk size of what is saved.

**Finishing an older plan at chunk size 0.** Its saved files have no chunk hashes: at 64 MiB every saved large file would be read again, hours for a large disk, while the archive's next registration gets 64 MiB anyway.

**A file's chunk rows with its row.** The chunk hashes are part of a saved file and of a recorded entry. A resume that reused a file without all of them would write a manifest that lacks chunk lines its chunk size requires, which the writer refuses (decision 0031) only after the whole read. Saved, read, reused and removed with the file's row, they cannot be left behind by one way of removing rows, nor be missing where the row is not.

**Schema version 2.** The tables are V1's; what changes is which rows they hold. A V1 program writes and removes only rows of `files`: in a repository that this version has filled, it would leave chunk rows behind and record revisions without Merkle roots, and its relocation writes a revision that this version rejects. Every program refuses a schema version it does not know, so raising it is the one way to keep a V1 program out.

**Upgrading without the write lock.** Every command opens the repository, and another process may hold the write lock for long, as the record of a large archive does (decision 0023): opening a repository that needs no upgrade must not wait for it.

**Waiting for another upgrade.** The upgrade holds the write lock while it copies the database (below): about 9 seconds for a database of 3 GB on the SSD of the computer that checked it, and longer on a hard disk. An open in another process meanwhile, as of the GUI started again because its window had not appeared yet (the GUI opens the repository before it shows its window, and each start is a process of its own), waited 5 seconds, as a statement does, and failed (exit 11), though the upgrade went on and succeeded. Reading the version between tries lets it go on as soon as the upgrade is committed, also while another operation takes the lock next. 2 minutes, as a record waits, cover the copy of a database of several gigabytes on a hard disk; a process that keeps the lock longer, or never lets it go, makes the open fail rather than wait for ever.

**A copy before the upgrade.** The verification history lives only in the database: the manifests rebuild the index (R-80), never the history (R-18). An upgrade goes forward only (R-92), and a program of the version before refuses the upgraded database, so the copy is what that program can still open, with the history as it was, until the operator is sure of the new version; a backup of RepositoryRoot (R-86) may be old or missing. Made in the transaction that upgrades, the copy holds exactly the database upgraded: one made before the write lock could miss a run that another process recorded in between. A name with the version and the day says what the file is to anyone who sees it beside `veriarchive.db`, and the day is the one people read (decision 0017). Without the copy the operator decided that the database is not upgraded: the history would otherwise go where no earlier program follows it.

**What `archive show` shows comes from the manifests.** The Merkle root is a revision's integrity value; the index's copy of it is an index (R-14), as is its copy of the header, which `archive show` never takes for the manifest's either.

**The same read.** A file's chunk hashes come from the buffers that give its file hashes (decision 0031, point 3): a FULL verify reads each byte once, by chunk or not, and a revision without a chunk size costs no chunk work.

**Which chunks differ, and from which byte.** A FULL verify that found a disk image of 200 GB `Modified` said only that its content differs. The chunks that differ say how much and where: one damaged sector is one chunk, a copy that broke off is every chunk from one on, a file rewritten is all of them. The byte where the first begins finds the place in any tool that reads at an offset; the `idx` is the chunk lines', which QUICK and DEEP will sample. Runs, and no more than ten of them, keep the detail one line however much differs ("chunks 0-3199 of 3200 differ"); `--json` gives every chunk.

**A size change stays one.** Bytes added or removed move every chunk after them: chunk hashes would name all of those, which says no more than that the size changed.

**A warning, not a failure.** Content is the integrity criterion (R-51), and both file hashes show it unchanged; a chunk hash that does not match it shows the manifest wrong, not the file. `FAILED` would send the operator to restore a file that is fine; `PASSED` would hide that its chunk lines, which QUICK and DEEP will compare, are wrong. A new revision is the remedy, as for content that changed: it is a new full scan. The other half holds for the same reason: the chunk hashes are BLAKE3 hashes of every byte of the file, read in the same pass, and each of them matching shows the content unchanged; a file hash that does not match it shows the manifest wrong. One file hash or both makes no difference: each covers the same bytes the chunks cover. Without chunk lines, nothing but the file hashes vouches for the content, so a file hash that does not match is a content that differs, as before.

**A warning of the run, not an item status.** An entry's item status says what its content is (§A6), and this file's content is verified. Its chunk lines are a defect of the manifest, as a media copy that differs is one of the copy (R-89), which is a warning of the run too. And one status per entry would have to choose between this and a difference of the file's metadata.

**Not checkpointed.** A checkpoint spares a read after an interruption (R-104); a resume that skipped such a file would lose its warning and say `PASSED`.

**A relocation compares whole files.** It accepts a carrier only when every entry matches by its file hashes and refuses it at any difference (decision 0004), and its refusal lists entries: naming chunks would change nothing of what it does. Comparing chunk hashes there would need a rule for chunk hashes found wrong: carried into r(N+1), a revision written knowing them wrong, or replaced by those read, which a relocation, carrying rN's hashes (decision 0004), does not do. The FULL verifications of r(N+1) compare them, as those of rN did.

Rejected alternatives:

- Keeping chunk size 0 for new revisions of archives registered by V1, until a FULL verify adds chunk hashes: the operator decided that new revisions use 64 MiB.
- Choosing the chunk size at each attempt of a registration: an attempt could not reuse the chunk hashes another saved, and a manifest could mix chunk sizes.
- Finishing a plan of an older version at 64 MiB: every saved large file would be read again.
- Chunk hashes in rows written and removed apart from the files' rows: one more thing for every way of removing rows to remember, and a saved file could be reused without its chunk hashes.
- An upgrade that reads the manifests, to index the chunk lines of revisions that a V1 program imported: V1 wrote none and could import only one that this stage or a later one wrote, which `repo rebuild-index` indexes; the upgrade stays a script of SQL in one transaction (R-92), which holds the write lock for the copy of the database and the script alone.
- Keeping schema version 1: a V1 program would go on operating the repository and make its index disagree with its manifests.
- The copy with `VACUUM INTO`, which the operator named as one way: SQLite does not sync its output, so after a power failure the copy of a database already upgraded could be incomplete; the backup API's copy is committed and synced like any database.
- Copying the database file with the file system: the WAL holds committed pages that are not in the file yet, and another process may checkpoint while it is copied.
- The copy in `cache/`, which §B7.1 calls disposable, or in `logs/`: beside `veriarchive.db` is where anyone looks for the database.
- The UTC date in the name: near midnight it is another day than the one people read.
- An open that fails once a statement has waited 5 seconds for the write lock, as this decision first had it: an open in another process while the database was copied failed, though the upgrade succeeded.
- Waiting for the write lock without a limit: a process that keeps it, such as one that hangs, would keep every open waiting, the GUI's without a window.
- Replacing a copy of the same name: it may be the only one left of that database.
- Upgrading without the copy, with a warning, when it cannot be made: the operator decided that the database is not upgraded without it.
- Removing the copies later: each costs the size of a database, once per upgrade, and only the operator knows when one is no longer needed.
- Saying where the copy is at every open: it is said once, by the open that made it; the user guides say where such copies are.
- A relocation that computes chunk hashes from what it reads, to carry or to compare them: it carries rN's hashes (decision 0004), and compares whole files (point 10).
- `archive show` from the index (`archive_revisions.merkle_root`, `chunks`): R-14.
- Comparing chunk hashes in a comparison: a copy registered at another chunk size, or by V1, would differ though its content does not; the whole-file hashes cover all of it.
- A command-line option for the chunk size: the operator fixed 64 MiB; smaller sizes are for tests (decision 0031).
- A second read of a large file for its chunks: the archive's largest files read twice.
- Naming every chunk that differs in the detail: thousands for a disk image rewritten; `--json` gives them all.
- Counting chunks from 1 in the detail: the chunk lines, `--json` and the byte the detail gives count from 0.
- `FAILED` for chunk hashes that do not match a file that matches: the file is fine; the operator decided `PASSED_WITH_WARNINGS`.
- `Modified` ("content differs") for a file hash that does not match a file whose chunks all match, as this decision first had it: every byte of the file is shown unchanged by its chunk hashes; the operator decided `PASSED_WITH_WARNINGS` (2026-10-17).
- Accepting such a file in a relocation: a relocation compares whole files and carries rN's hashes (decision 0004), so it would carry a file hash known to be wrong into r(N+1), or would have to take the one read, which a relocation does not do.
- An item status of its own for such a file: its content is verified, and an entry has one status.
- Checkpointing such a file: a resume would lose its warning.
- Marking in a run's record (`run:<run_id>`) that its checkpoints were made by chunk, so that a resume reads again the large files of an earlier version's run: only a revision with chunk lines that an earlier version verified would need it, which V1 had only by importing a manifest of this version's; that run's checkpoints say that the content matched, which is what a FULL verify proves, and the next FULL verify compares their chunks.

## Consequences

- Amended by decision 0033: the FULL verify that adds chunk hashes to an archive registered by V1 (point 6) is `verify --full --add-chunk-hashes`; it records the next revision only when every entry matched, with rN's entry lines byte for byte and their chunk lines. The schema version is 3, which adds `verify_progress_chunks`: a program of schema version 2 refuses a repository that a program of decision 0033 has opened.
- The manifest format and its version (1) are unchanged, and so are the golden manifests that the unit tests write: the engines fill what §B4 has (decision 0031). A registration's manifest now names chunk size 67108864 and a Merkle root, with chunk lines for every file larger than 64 MiB; a relocation's names rN's. So does the golden tree that the end-to-end test registers on every system (R-66, `tests/golden/golden_tree_r0001.vam`): its header gives chunk size 67108864 and the tree's Merkle root, and its entries, none larger than a chunk, keep their bytes.
- The database schema is version 2, with the tables of version 1. A V1 program cannot open a repository that this version has opened, and there is no way back (R-92: migrations are forward-only); the copy of the database kept before the upgrade, and a copy of RepositoryRoot taken before (R-86), are what a V1 program can still open.
- RepositoryRoot holds the copies kept before upgrades (`veriarchive-schema-N-before-upgrade-<date>.db`), in WAL mode as their database was, so that opening one makes its `-wal` and `-shm` files beside it; nothing reads them, and a backup of RepositoryRoot (R-86) holds them too. An upgrade needs room for one more database beside it, and takes the time of copying it, once, while an open in another process waits for it, up to 2 minutes; the GUI, which opens the repository before it shows its window, shows it once the copy is made, or once the other process's upgrade has ended; without the room, the repository stays at its version, for the program of that version, and the open fails (exit 11).
- Core: `SchemaUpgrade` and `AppContext::schema_upgrade`, what an open upgraded and where the copy is; `open_repository` and `initialise_repository` take the local date that names the copy (`today`); `SqliteDatabase::copy_to`; `UpgradeLockWait`, how long an open waits for the write lock to upgrade (5 seconds a try, for up to 2 minutes; shorter only in tests), which `open_repository` takes. App: `local_date`, `Session::notes`, `schema_upgrade_note`, `SessionOptions::now` (the moment the repository is opened at, whose local date names the copy: the system clock's, which tests set). CLI: the note on stderr. GUI: the note in Settings, shown first after the open that upgraded. The GUI's part has no unit test of its own (GTK): its words are `schema_upgrade_note`'s, which the tests cover in both languages.
