# The verification report of a run is one HTML file

What a verification found was in the repository alone: the window's result page of the run (decision 0046) and the command line's `verify` and `history` said it, and nothing gave it as a file to keep with the archive's papers or to send to someone who has no VeriArchive. With the window's redesign the owner asked for it (plan of 2026-11-04: "HTML verification report of one run (+ run list + chain status), from the result page '儲存報告…' and a CLI command; only runs with a result; devices named by model and serial"), and the approved prototype shows 儲存報告… on the result page, what the file is for ("存成一個 HTML 檔（驗證報告），可以直接用瀏覽器打開，或寄給別人") and, for a run that did not finish, "未完成的驗證不能儲存報告". This record states what was built (3441cc2, with the footer's check and the command line's refusal of a file made meanwhile completed after it).

## Decision (operator, 2026-11-04)

1. **A verification report is one self-contained HTML file of one recorded run that reached a result** (GLOSSARY: Verification report): `PASSED`, `PASSED_WITH_WARNINGS` or `FAILED`. An `INCOMPLETE` run has none, as it claims nothing (§A6: an `INCOMPLETE` run makes no PASS/FAIL claim): its result page says "A report cannot be saved for a verification that has not finished." and offers no Save report..., and `report` refuses it. The file:
   - is UTF-8, starts with `<!doctype html>`, sets `lang` to the language it is written in, and holds its style inline (CSS only); it holds **no script and loads nothing from elsewhere** (no style sheet, font, image or frame of another file or server);
   - escapes every value (`&`, `<`, `>`, `"` and `'` as references), and shows an invalid UTF-8 sequence and every control character but tab and line feed, the C1 controls (U+0080 to U+009F) included, as U+FFFD, so that a path, a label or a serial that holds them cannot change the page or hide in it;
   - reads on screen in a light and a dark style, as the system asks (`prefers-color-scheme`), and prints on A4 in the light style with nothing that needs a background to be read, the header of a long table repeated on each page; paths, UUIDs, hashes and serials are in monospace; a result is said in its words, with a mark (✓, !, ✕) beside its colour, never by colour alone;
   - draws the read speed chart, where the result page draws one, as inline SVG from the same numbers (`SpeedChart`, `chart_stretches`), with its legend and the words of its axis, and otherwise gives the page's words why there is none;
   - is the same, byte for byte, for the same records made into a report at the same time in the same time zone, which the unit tests compare.

2. **It says what the run's result page says, in the same words, from the same records**, and what the owner asked for besides:
   - **As the result page**: the result with its mode ("FULL VERIFY PASSED"), the archive (label and volume label) and when the run ended, in local time with its offset (decision 0017); the banner's lines (PASSED's "100% of the registered content was read and matched", each failure of the run, what else the run is: a relocation's, a carrier confirmation's, decision 0047); the device alerts (decision 0044); the figures; the read speed and what it was compared with; the items in the page's order (those that fail the run, then those that warn, then those that change no result), first for a run that `FAILED` or `PASSED_WITH_WARNINGS`, every one of them, as a report is a record (the window lists them 200 at a time); Device and identity (the media identity, the volume and its devices with model, serial, "Enclosure serial" where the enclosure hides the device's own, WWN, bus and the health each reported); Technical details (the run's id, mode, revision, the run it resumed, the chunk hashes added, when it started and finished, the entries by status, the bytes matched, the failures, the computer and the program version that recorded the run, and the guarantee, R-02); and, below the banner, the archive's label and whole UUID.
   - **The device's own identity read behind its enclosure**: for a run that went on past a changed enclosure after the device identity reader read the device (decision 0047), the model, own serial and WWN that its carrier confirmation records, under "The device's own identity, read behind its enclosure". Only the report shows it; the window's result page does not (open question 2).
   - **The archive's runs**: "Runs of this archive (N)", every recorded run of the archive, `INCOMPLETE` ones included, newest first, each with when it finished and its run id, its result with its mode, its revision and its notes (what else the run is, its device alerts); the reported run in bold and marked "This run" in words.
   - **The history chain when the report was made**: the same recomputation as `repo verify-history` and History's Check history chain (`ArchiveStore::check_history`), over the history of every archive of the repository: "The history of every archive is intact: N verification runs, hash chain verified.", "History BROKEN at run X (ARCH-0001 · <time>): ...", or why it could not be checked; with what such a check cannot detect (`history_chain_limits`), and this run's `row_hash` as "This run's hash in the history chain (row_hash)".
   - **The footer**: "Made <time> on the computer <name> by VeriArchive <version>.", and that the repository is the record: the file says what the repository recorded when it was made; it is not signed, so it cannot show a change made to it afterwards; to check it, make a new report of the run from the repository (Save report... on its result page, or `veriarchive-cli report`) and compare the two: what they say of this run, this run's hash in the history chain and the chain's state. Only what they say shows whether the file was changed: the same `row_hash` and an intact chain show only that the run's row in the history is unchanged (its result, figures, failures, computer and version: `verify_run_hash_input` holds neither its items nor its media evidence), and nothing of the file, which no hash covers.
   - It is read in one read transaction of the database, so that its parts are of one moment: the run, its items, its archive's runs, its media evidence, the archives named as the views name them (`display_label`, with the start of the UUID where a label is shared, R-88), the chain checked, and the first run of a broken chain, by which it is named. The volume label of the archive's current carrier comes from its latest manifest, as the views name it for a run whose evidence names none.
   - Its language is the window's, or on the command line that of `--lang`, else as every command chooses it (decision 0017).

3. **One source of every sentence.** The window's result page and the report must say the same, and the command line must make the same file, so the result page's model moved from `src/gui` into `src/app`, and both render it:
   - `app/run_words.*`: tones, pills, fields (with a mark for monospace, which the window ignores), the guarantee, the words of bytes, buses and durations, `result_with_mode` and `result_tone`, from `gui/archive_rows`, `gui/report` and `gui/run_result`;
   - `app/run_result.*`: the whole model, moved as it was (`RecordedRun`, the items' tones and order, `SpeedChart`, the axis, `run_read_speed`, `stopped_percent`, `ResultPage`, `result_page`), with `read_recorded_run`, which the window's page now uses too, `chart_stretches`, shared by the window's chart and the SVG, `ChartWords` and the headings Device and identity and Technical details, which both render from the model, `ResultPage::confirmed_device` (point 2), and `no_report_of_incomplete`, the one sentence that the page says and the report refuses with;
   - `app/shown_identity.h`: `ShownIdentity`, the parameter by which the window's screenshot mode gives its sample devices, volume and computer (the gui adapts its `IdentityShown` to it), as recorded otherwise;
   - `ChainShown` and `chain_words`, from `gui/history_rows` into `app/history.*`: History and the report say the chain's state in the same words.
   The gui keeps only the window's own: the tones as style classes, the pill widgets, Resume of a stopped run and the screenshot mode's sample identities; its old names stay as aliases, so the page and its tests are unchanged. The HTML writer is `app/run_report_html.*`, without GTK; the root guard is `app/archive_roots.*` (point 7). `veriarchive-cli verify` takes R-02's sentence from `app::guarantee`, where it wrote the sentence out itself. The words that only the report has (the columns' headings, the run list, the chain's heading, the footer, the device's own identity) are in the catalog with the rest.

4. **The name the window proposes**: the archive's label, "verification report", the local date on which the run ended and its result, in the window's language: `ARCH-0001 verification report 2026-11-04 PASSED.html`, `ARCH-0001 驗證報告 2026-11-04 通過.html` (open question 3). Every character that a file name cannot hold on Windows (`\ / : * ? " < > |` and the control characters) becomes `_`, and the words before `.html` end with no space or dot. The command line takes the file named by `--out`.

5. **The window.** The banner of the result page of a run that reached a result offers **Save report...** (儲存報告…), with the tooltip "Saves what this page says as one HTML file, a verification report, which a browser opens and which can be sent to others." It opens the system's save dialog (`GtkFileDialog`, GTK 4.10, within the 4.14 ceiling), "Save the verification report", with the name of point 4 in the folder that a report was last saved into in this window, remembered only after a save that succeeded, else the user's Documents folder, else the home folder, and the filter HTML file (`.html`, `.htm`); the dialog asks before it replaces a file there. A folder in an attached archive's root is refused in a message (point 7). The report is then made and written off the window's thread (`read_off_thread`: the database opened read only, the platform's atomic writer, whose `commit()` replaces the file the dialog agreed to replace as a whole).
   - **No progress and no cancel**: making a report is one read and one file, not a long operation, so it takes no `IProgressSink` or `CancelToken` (CLAUDE.md's rule 7, R-94), as decision 0046 (point 8) says of the retirement and its preview. The file is small unless the run recorded many items: it lists every one (`verify_items` keeps every item that is not Verified, without limit, HANDOFF D7), about 100 bytes of markup besides its path and detail each, so a run that found most of a large archive Missing or Modified makes a file of hundreds of MB, built in memory with no progress (open question 5). It reads the run's records and checks the chain in one read transaction, the chain's check reading the repository's runs once, as Check history chain does, and the archives' latest manifests for the root guard, the read that every refresh of Archives makes without cancel or progress.
   - **Then a toast**: "Saved report: <file name>" with **Open**, which opens the file as the system opens an HTML file, in a browser (`gtk_file_launcher_launch`), "Cannot open <name>: <why>" where it cannot; a failure, "The report <name> was not saved: <why>", the why of a run gone from the records meanwhile, as after `repo rebuild-index`, being "This run is no longer recorded."; a folder that the check off the window's thread refuses (point 7) is said in a message, as the refusal at once is, not in a toast.
   - **The screenshot mode** shows the button; the tour saves the report of the run its result page shows, as Save report... saves it once a file is chosen, into its folder as `report-sample-<language>.html`, sample data with the sample identities and the computer `SAMPLE-HOST`, which `make_screenshots.cmake` moves out of `docs/images` into its `WORK` folder: it is no picture of the guides. The smoke tests make a report from fixed sample facts in both languages and check it.

6. **The command line**: `veriarchive-cli report <run_id> --out FILE.html`, with the global `--json` and `--lang`. The run is named by its whole id, as `history <uuid>` lists it and `verify --json` gives it (`run_id`); the window shows it under Technical details. `report` records nothing: it opens the repository as every command does (the first open by a new version upgrades a database of an older one, keeping a copy, decision 0032), then reads the run's records through the database opened read only (`ArchiveStore::open_read_only`); it adds no run, changes no history and reads nothing of an archive's content. It writes FILE through the atomic writer, which gives the file its name only where nothing of that name is there (`write_new_file_atomically`, `IOutputFile::commit_new()`), its path as typed (CLAUDE.md's rule 4). Like the window, it shows no progress and takes no cancel: Ctrl+C ends it as it ends any program, and the atomic writer then leaves no part of FILE: either no FILE, with at most its temporary file (`FILE.tmp-<pid>-<n>`) beside it, or, once it was named, the whole of it (point 5).
   - **Exit `10`**, each saying why and writing nothing: a usage error ("usage: report <run_id> --out FILE.html", an unknown option); a FILE that is there already ("FILE exists already; a report never replaces a file, so name another one"), told before the repository is opened, and in the same words where the writer's commit finds one made meanwhile; a run that is not recorded ("no run X"); an `INCOMPLETE` run ("run X did not finish (INCOMPLETE); a report is made only of a run that reached a result"); a FILE in the root of an attached archive (point 7). An unknown run and an `INCOMPLETE` one are usage errors, as `export-sha256sums` refuses an archive that is not registered ("no archive X", exit `10`; open question 4).
   - **Exit `11`**: a repository that cannot be opened or read, and a FILE that cannot be written.
   - **Exit `0`**: "Wrote the verification report of run X (ARCH-0001: FULL VERIFY PASSED) to FILE"; with `--json`, `{"run_id", "archive_uuid", "result", "out"}`, and an error as every command's (`error`, `exit_code`).
   - **`report` never replaces a file**: the file there may be another run's report, and the command line cannot ask, as the window's dialog does. It looks for FILE before it opens the repository, and its writer's commit refuses again, in the call that names the file, a FILE that another program made while the report was made: `IOutputFile::commit_new()` renames the temporary file without replacing anything (Windows: `MoveFileExW` with `MOVEFILE_WRITE_THROUGH` and without `MOVEFILE_REPLACE_EXISTING`; Linux: `renameat2` with `RENAME_NOREPLACE`, or, where the file system refuses that flag, a hard link of the temporary file under FILE's name and then the temporary name removed, and the directory synced as `commit()` syncs it; a link that NFS answers with `EEXIST` after making it, as `link(2)` warns where a reply is lost, counts as made where FILE names the temporary file itself, the same device and inode). Where anything of that name is there, a file, a folder or a link, it fails with `IoErrorKind::AlreadyExists` (Windows `ERROR_ALREADY_EXISTS` or `ERROR_FILE_EXISTS`, Linux `EEXIST`, which the platform now maps to that kind wherever it meets them), leaves what is there as it was, names nothing and removes its temporary file; `report` then exits `10` as above. One narrow window is left, on a Linux file system that takes neither `RENAME_NOREPLACE` nor hard links (such as exFAT through FUSE): there the writer looks for the name and then renames, and a file made under that name between the two is replaced. `export-sha256sums`, by contrast, replaces its FILE without asking (open question 1).

7. **Never into an attached archive's root.** A report saved in the root of an archive attached now, or in a folder below it, would be an entry that the archive's next FULL verification reports as added (New), failing it, as if the disk were damaged; and where an archive is a whole volume (`H:\`), every folder of that volume lies in its root. The window and the command line refuse such a folder, naming the archive: "<folder> lies in the root of ARCH-0001 (<root>): a report saved there would add a file that its next FULL verification reports as added. Choose a folder outside every archive."
   - `app::roots_holding` finds the archives on the folder's volume as identity matching finds them there now (`where_attached` against every archive's latest manifest: `MATCH`, `MATCH_WEAK`, `MIGRATED` and `AMBIGUOUS` alike, each an archive's folder there). A root holds the folder as their paths are written (`path_within`), or as the file system names both (`platform::final_path`, decision 0029 point 6), so that a folder written through a symbolic link, a junction, a drive letter made with subst or a short (8.3) name is the folder that it names; the folder's volume is looked up through `platform::resolve_subst_drive` (decision 0027), and through the folder's final name where that lies on another volume (a link to a folder there). Where the volume or the archives cannot be read, nothing is refused.
   - The window refuses at once from the latest read of the attached devices, comparing the paths as written, so that the window's thread makes no call to the file system; then again off the window's thread, before the run is read or anything is written, with `app::roots_holding`. The command line refuses after the run is found.
   - **The window's export uses the same guard**: Export manifest... refused a folder in an attached archive's root (decision 0046, point 7) as the paths are written; its check on the job's thread is now `app::roots_holding`, so a folder reached through a link, a junction, a drive letter made with subst or a short name is refused too, in the export's own words ("an export there would add files that its next FULL verification reports as added").
   - The command line's `export` and `export-sha256sums` write where they are told, as before (open question 6).

8. **No change to the records**: no schema change, no manifest change, nothing recorded in the repository by a report (point 6), and no `--json` member of another command; a report reads what the history and the media evidence already record.

### Not in this decision

- No signature of the file: the repository stays the record, and V1.1's tamper evidence is not part of it.
- No PDF: the browser prints one.
- No report of several runs, nor of an archive's whole history: the report lists the archive's runs, and a run's report is made from its own result page.
- No report of an `INCOMPLETE` run (point 1).
- No change to the records (point 8).

### Open questions for the owner

1. **An existing file**: `report` refuses one, also one made while the report is made (exit `10`, point 6), as this decision's specification asked, while `export-sha256sums` replaces its FILE. Keep the refusal, or replace the file as `export-sha256sums` does? The window's save dialog asks before it replaces a file either way.
2. **The device's own identity on the result page**: the report shows the device's own model, serial and WWN that a carrier confirmation of decision 0047 read; the window's result page does not, as that page was not to change in this decision. Show it there too? It ties to decision 0047's open question 4, the row Device's own serial in Archives' details.
3. **The words "verification report" in the proposed name** (`ARCH-0001 verification report 2026-11-04 PASSED.html`, `ARCH-0001 驗證報告 2026-11-04 通過.html`): the specification named the label, the date and the result alone. Keep them?
4. **The exit code of an unknown and of an `INCOMPLETE` run**: both are `10` (usage error). Keep it, or give one of them another of the existing codes?
5. **A report of a run with very many items**: the report lists every item, as a record should; for a run that found a large part of an archive Missing or Modified, the file grows to hundreds of MB, too large to mail and slow to open, and is made with no progress or Stop (point 5). Keep it so, or list a limited number of items of each status with their counts?
6. **The command line's exports in an archive's root**: `export` and `export-sha256sums` still write where `--out` points, also into the root of an attached archive or a folder below it (point 7), and this decision does not change them. The user guide tells a reader to run `sha256sum -c` from the archive's root, so a sums file saved there is a natural mistake, and it is then an entry that the archive's next FULL verification reports as added, failing it. Should they refuse such a folder, as `report` and the window's export do?

## Why

One file that holds no script and loads nothing is what the owner asked for and what such a file is for: it opens in any browser, offline, on a computer without VeriArchive, years later as on the day it was made; it can be mailed and kept with the archive's papers; opening it runs nothing, so whoever receives it can open it safely, and a mail program has no script to strip or block; and it shows nothing to a server when it is opened. HTML, not PDF, because the browser prints it and saves it as a PDF, while a PDF writer, with the fonts it needs for Chinese, would be a library to bundle (R-121); and its text can be searched and copied.

It says what the result page says from the same model because two renderings of one run must not say two things: the words are worded once, translated once, and tested once, and the command line makes the same file, so a script can make one. A report is a record, so it lists every item where the window lists 200 at a time.

The archive's runs and the chain's state were the owner's request: a run's result reads differently beside the runs before and after it. A new report of the same run from the repository lets a reader check the file later: the same `row_hash` and an intact chain show that the run's row in the history is unchanged, and what the two say of the run shows whether the file is; as the file is not signed, it proves nothing by itself, and says so. A run that did not finish has no result to report (§A6).

A report saved into an archive's root would fail that archive's next FULL verification, and saving a report next to the data it speaks of is natural; the export already refused that folder, and a folder reached through another name of it, which the file system follows, is the same folder.

Rejected alternatives:

- A PDF: a library and fonts to bundle; the browser makes one from the HTML.
- A script in the file (sorting, filtering, folding the items): a mailed file that runs code, which mail programs block, and a page that shows less when it is blocked.
- A linked style sheet, a web font or an image: not readable offline, and a load from a server tells it that the file was opened.
- A report of an `INCOMPLETE` run: it reached no result (§A6).
- A report of several runs, or of an archive's history: not asked for; the run list names every run.
- Signing the file: V1.1's signatures and trusted keys (§B5), not built.
- Giving `row_hash` in `history --json`, so that a reader could check a run's record without a new report: it changes an output of §B16, and it would show only that the run's row in the history is unchanged, never whether the file was changed, which only a new report compared with it shows (point 2).
- The window wording its page and a second writer wording the file: two sources of every sentence.
- Replacing an existing file on the command line, as `export-sha256sums` does: the file there may be another run's report (open question 1).
- Looking for FILE only when `report` starts: the repository's open (which may copy the database for an upgrade), the chain's check and the making of the file lie between the look and the commit, and a FILE made then, as by a second `report` to the same name, would be replaced at a commit that replaces.
- A progress bar and Stop for making a report: it is one read and one file, long only for a run with very many items (point 5, open question 5).

## Consequences
