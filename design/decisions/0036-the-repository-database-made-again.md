# The repository database is made again from the manifests

R-80 promises that `manifests/` and the user config are enough to rebuild every index table with `repo rebuild-index`, and both user guides gave it as the fix for a damaged database. It could not do that. The rebuild opened the database first, so where `veriarchive.db` was missing it stopped with "cannot open repository database: unable to open database file", where it held other bytes with "cannot prepare SQL: file is not a database", and where it was a file of 0 bytes with "unsupported repository schema", each exit 11; `repo init` and every other command stopped the same way. The only way out, which no document described, was to move `repository.json` aside and make a new repository, which gives the repository another uuid, and then to import each manifest.

## Decision

1. **What the database is.** Before it rebuilds, `repo rebuild-index` reads what is at `veriarchive.db` (`database_state`, read only):
   - usable: a database of this version's schema;
   - missing: no file;
   - empty: a file of 0 bytes, or a database without any table;
   - not a database: SQLite does not read the file as one ("file is not a database");
   - damaged: SQLite reads it as a damaged one ("database disk image is malformed"), also beyond its first page (amended 2026-10-27): before it rebuilds, `repo rebuild-index` reads every page with SQLite's `PRAGMA quick_check`, and a result other than "ok" is damage; and a database of this version's schema (`schema_version` 1) that lacks one of its tables, all of which this version creates in one transaction;
   - unfilled: a database that a rebuild made again (point 2) and that no rebuild has filled yet, as it still holds the mark it was made with (amended 2026-10-27, point 7).

   Anything else is an error that changes nothing, exit 11 as before: a database that cannot be read now (locked by another program, access denied, a disk error), and one that holds another program's tables or another version's schema ("unsupported repository schema"), such as a later version's: it may hold what this version cannot read, so nothing ever replaces it.
2. **Made again.** A database that is missing, empty, not a database or damaged is put aside and made again, in the repository's own folder. The new database, of this version's schema, as `repo init` creates one, is made first beside the old one, as `veriarchive.db.new`, and with it, in the transaction that creates its tables, its mark: the setting `rebuild:replaced-database`, which says why the old one was replaced and the name it is put aside under (`{"state":"damaged","moved_to":"veriarchive.db.damaged-..."}`, `moved_to` null where it was missing). Then `veriarchive.db` is renamed `veriarchive.db.damaged-<UTC date and time>` (`veriarchive.db.damaged-2026-10-27T10-15-30Z`, with `-2`, `-3`, ... where that name is taken), together with the files SQLite keeps beside it (`-wal`, `-shm`, `-journal`, also where the database itself is missing), so that the new database never takes up the journal of the old one, and the new one is renamed into its place. It is made in SQLite's rollback-journal mode, whose commit leaves nothing in a `-wal` file that would not move with it, and put in WAL mode (R-91) in its place. The rebuild fills it from `manifests/` (R-80) and takes the mark away in the transaction that fills the index. Nothing is deleted but a `veriarchive.db.new` that a rebuild left before it moved anything aside, which holds nothing but its tables and mark. The repository keeps its uuid (`repository.json` is not touched), so the pin's record (R-83 step 5) and the hash chain's first link (R-90) stay right.
3. **What the manifests give back.** Every archive that `manifests/` holds a readable manifest of is listed again: its uuid; its label and root as its latest manifest records them; when its first revision was registered; its latest revision, every revision and the index. What only the database held is not given back, as R-80 says of the history tables: the verification history (each archive is listed as never verified until it is verified again, and a new hash chain starts), which archives were retired (each is registered), the plans and saved progress of unfinished registrations and relocations, and the label sequence, which point 6 makes harmless. An archive whose manifests are all gone is not listed.
4. **Said plainly.** The rebuild says what was wrong and where the old file went, "The repository's database was damaged; it was put aside as P and a new one was made." (or "was missing; a new one was made.", was empty, was not a database), then its usual lines ("Rebuilt the index from manifests: ..."), then: "The verification history was kept only in the repository's database, so the manifests cannot give it back: every archive is listed as never verified until it is verified again, an archive that was retired is listed as registered, and unfinished registrations and relocations are gone. If a backup of the repository holds veriarchive.db, put that file in place of the new one and run `repo rebuild-index` again." It exits 2, as a rebuild that skipped a manifest does: it worked, and the operator has to know. Its `--json` gives `replaced_database`: null, or `state` (`missing`, `empty`, `not_a_database`, `damaged`) and `moved_to` (null where the database was missing). A rebuild that fills a database made again by a rebuild before, which did not finish (point 7), says the same of the database put aside then, as its mark names it.
5. **Named everywhere else.** Every other command, `repo init` too, and the GUI, which open such a repository, stop as before (exit 11), now saying what is wrong and what to run: "the repository's database P is missing; make it again from the manifests with `repo rebuild-index`" (or is empty, is not a database, is damaged), and of a database made again whose rebuild did not finish (point 7), "the repository's database P was made again, but its rebuild from the manifests did not finish; finish it with `repo rebuild-index`". The archive lists say the latter too (`archive_statuses`), so that a GUI opened before the database was made again shows it in its Archive List, never an empty repository. **Damage met later** (amended 2026-10-27): opening the repository reads the database's first page, its schema and the mark alone, not every page, which would read all of a large database at every command; a damaged page elsewhere, of a table or an index, is met where a command reads it. Wherever SQLite then reports the database damaged or not a database (`SQLITE_CORRUPT`, `SQLITE_NOTADB`; `IoErrorKind::DatabaseDamaged`), the command says so in the same words, "the repository's database P is damaged; make it again from the manifests with `repo rebuild-index`" (or is not a database), exit 11 as before, where it said "cannot run SQL: database disk image is malformed" and named no way out; the GUI shows the same. `repo rebuild-index` reads every page first (point 1) and makes such a database again before it rebuilds; damage that `quick_check` does not see, such as an index that does not agree with its table, which the rebuild meets as it rewrites the index, makes it put the database aside as damaged, make it again and rebuild once more into the new one (`rebuild_repository`), as no rebuild could otherwise get past it. `repo init` does not make the database again itself: the repository exists, and only the rebuild says what is lost.
6. **An automatic label never repeats one in use** (R-33). A registration without `--label` takes the next number of the repository's sequence (`settings.next_label_seq`), which knew nothing of the labels in use: a label typed earlier (`--label ARCH-0002`) was given again to the next archive registered without one, and a database made again (point 2) starts the sequence anew, so the next automatic labels would repeat every label that the manifests gave back. An automatic label now skips every number that a label of the repository already has, typed, imported or given back by a rebuild, the number read from the digits after `ARCH-` (`ARCH-00004` has the number of `ARCH-0004`, and a label without such digits has none). Labels stay without a uniqueness constraint: one typed twice is recorded twice (R-33, R-88).
7. **Progress and cancel** (R-94). `repo rebuild-index` reads every manifest of the repository, which takes minutes where they hold millions of entries, and took neither a progress sink nor a cancel token. It now reports the manifests it reads (one report before the first, one at every 1000 entries read and one after each manifest, with their bytes as listed and the manifest's name), which the command line shows on stderr ("reading manifests: 3/40"), none with `--json`. A cancel (Ctrl+C) is asked before each manifest and each entry, and between the archives written in its one transaction, which it then rolls back: a cancelled rebuild changes nothing of the index, says "the rebuild of the index was cancelled; the index was left as it was" and exits 4. **A rebuild that stops after it made the database again** (amended 2026-10-27), cancelled, failed or ended with its process, leaves the new database with its mark (point 2), unfilled: every command names the rebuild for it (point 5). It says which database it put aside and what is lost (point 4), and then "the rebuild of the index was cancelled before it filled the new database; no command can use the repository until `repo rebuild-index` runs to its end" (exit 4), or, where it failed, "the rebuild of the index did not fill the new database, and no command can use the repository until `repo rebuild-index` runs to its end: <cause>" (exit 11), with `replaced_database` in its `--json` beside `error` and `exit_code`. The next rebuild puts nothing more aside, fills the database, and says what point 4 says of the database put aside then, as the mark names it, exit 2. One that ended between moving the database aside and moving the new one into place left the database missing and the new one beside it: the next rebuild takes the new one up, mark and all, unless a journal is left beside the place, which it would take up; then it puts the journal aside and makes the database again, the database put aside before then named by its file alone.

## Why

The manifests are the truth (R-14) and the database an index: a lost index must not make a repository unusable, and the operator must not be asked to make a new repository, with a new uuid, to get the manifests listed again. The rebuild is the command that already rebuilds the index, and the guides already sent the operator there.

The old file is put aside, never deleted: a damaged database may still hold most of the history, which someone with SQLite's own tools may read, and a backup restored later replaces the new database as the message says. Its name keeps its own and says when it was put aside, so several such files can lie side by side and none is mistaken for the database.

Only the states that cannot be read as a database of this version are replaced. A locked database belongs to a running program; a database of another version's schema belongs to that version (a later version may upgrade the schema, and this one must leave such a database alone); another program's tables mean that the file is not the one this repository made, which the operator should look at. A rebuild never turns those into an empty database.

A label is written on the device's case and read by people (decision 0025): two archives under one label are told apart only by their uuids, so the program never makes such a pair itself. The sequence stays the source of the numbers, and the labels in use only push it on, so the archives listed in one repository keep the numbers they have; reading the labels at each registration costs one query over the archives.

Exit 2, and the history named in so many words: a rebuild that made the database again worked, but every archive now reads as never verified, and the operator who has a backup should use it instead.

Every page is read by the rebuild alone (point 1): `quick_check` reads each page once, which a rebuild, reading every manifest and rewriting the index, can afford, but not every command; SQLite's own error where a command meets a damaged page is as sure a sign, and it now names the way out. `integrity_check`, which also compares every index with its table, was not taken: it looks each row up in each index, many reads at random places of a large database, which on a hard disk takes far longer than the rebuild itself, and the one damage it adds, an index that does not agree with its table, the rebuild meets and handles itself (point 5).

The mark (point 7): the repository holds the operator's only verification history, so a rebuild that stops must never leave what looks like an empty repository. Without it, a rebuild cancelled after it made the database again said "the index was left as it was" (exit 4); the folder then held a new, empty database and the old one put aside, `archive list` said "No archives registered." (exit 0), the next rebuild exited 0 without naming the file put aside or the history lost, and `register` of a folder already registered made a second archive under the same label. The mark is written with the new database's tables and taken away with the index filled, each in one transaction, so no stop leaves a new database that does not say it is unfilled; and as it keeps the name the old database went under, the rebuild that finishes says what the one that made it would have said. The new database is made beside the old one and moved into place last, so that a stop before then leaves the old one where it was, and the moment in which the database is missing is the one between two renames.

Rejected alternatives:

- Making the database again in `repo init`: init finishes a repository that a crash left unfinished (decision 0011); here the repository is complete and only its index is gone, which is the rebuild's work, and init would say nothing of the history lost.
- Asking for `--confirm` first: nothing is deleted, the database cannot be used as it is, and the rebuild's own output says what is lost and how a backup brings it back.
- Repairing a damaged database in place (SQLite's recovery): the result is a database whose history cannot be trusted, which R-18's hash chain would then contradict or hide; the old file stays for such work outside VeriArchive.
- A new repository uuid: the pin's record would warn (R-83 step 5), and nothing about the repository changed but its index.
- Filling the new database under its own name and moving it into place only once filled (point 7): the rebuild and every connection open the database at its place, a filled database in WAL mode would have to be checkpointed whole before it moves, and the moment between moving the old database aside and the new one in stays; with the mark, a stop at any point names the rebuild and the database put aside.

## Consequences

- `repo rebuild-index` recovers a repository whose database is missing, empty, not a database or damaged, keeping its uuid, its manifests and everything they record; the history and what else only the database held are lost, as R-80 and R-86 say, and the rebuild says so. Backing up RepositoryRoot (R-86) stays the only way to keep the history.
- The user guides describe the rebuild as making the database again, the file put aside, and what is lost, and say that automatic labels skip the numbers in use.
- Tests of damage beyond the first page (points 1 and 5): a sample archive's database with the first page of its table of files overwritten (sample damage) reads as usable when the repository is opened and as damaged when every page is checked; a command that reads that table fails with the plain words and the database's path; a rebuild given that database as usable meets the damage, puts the database aside as damaged, makes it again and lists the archive; the new database with its table of archives damaged so is put aside and made again when it is opened for a rebuild, which then fills it; a file that is no database checked for its schema, and this version's schema without one of its tables, which is damaged. A mutation check removed each rule in turn (the check of every page, its use by the rebuild, the plain words where SQLite finds damage, the rebuild that makes a database it finds damaged again, the incomplete schema as damage), and each removal failed the test meant for it.
- Tests of point 7, a rebuild that stops after it made the database again: a sample archive's database made again (sample bytes) is unfilled, named by opening the repository and by the archive lists; a rebuild cancelled with its first report, and one that fails (manifests/ moved away, sample damage), leave it so; the next opening for a rebuild names the database put aside before and puts nothing more aside; the rebuild that finishes leaves it usable and lists the archive again. A new database moved back beside its place (as a stop between the two renames leaves it, sample) is taken up, naming the database put aside before; a `veriarchive.db.new` left beside a database that cannot be used (sample bytes) is removed and the database replaced as any. The CLI end to end: a rebuild that fails after it made the database again (manifests/ moved away) names the database put aside, the history and the rebuild to run again (exit 11), and `replaced_database` in `--json`; `archive list` then names the rebuild that did not finish in either language (exit 11); the rebuild that finishes names the same database put aside and the history (exit 2), and the archive is listed. A mutation check removed each rule in turn (the mark written with the new database, the mark taken away by the rebuild, the unfilled state, the archive lists' refusal, the new database taken up, the one left removed, what a stopped rebuild says, the mark named by the next rebuild), and each removal failed the test meant for it.
- Tests of point 7: the reports of a rebuild of two sample manifests, one of 1001 entries, read through a fake file system that counts the bytes read; a rebuild cancelled with the report after the first manifest, which reads nothing more, one cancelled at the report at 1000 entries, which takes none of them and reports nothing more, and one cancelled at the last report while it writes the index, each leaving the index as it was; a mutation check removed each cancel and each report in turn, and each removal failed the test meant for it.
- Tests of point 6: the next automatic labels with sample archives labelled by hand, by import and twice with one label, which they skip, and a label without a number, which skips nothing; a mutation check that let the sequence give a number in use failed the test.
- Tests: the state of the database (usable; missing; 0 bytes and a database without tables, empty; sample bytes, not a database; its first page marked with a b-tree type that does not exist, damaged; another program's tables, a later schema and a locked database, errors), and what every command says of each state; the database opened for the rebuild where it cannot be used: put aside with its journal beside it, under a name that says when, made again where it was missing with a journal left beside it put aside, the uuid kept, a usable database and another program's left as they are; the rebuild into an empty database giving each archive its uuid, label, root, registration time, revisions and index from the manifests alone, registered, and the archive verifying again with a history of its own; the CLI end to end: a missing database named by `archive list` and `repo init` in either language, made again with the message and exit 2, the archive listed with its label and never verified, the repository's uuid kept, and verifying again; a database that is not one, put aside with its bytes kept, `replaced_database` in `--json`; an empty one in Chinese; a usable one not replaced. A mutation check removed each rule in turn (the replacement, the files beside the database moved, the empty database, a file that is not a database, a damaged one, the message of every command, the history named, exit 2), and each removal failed the test meant for it.
