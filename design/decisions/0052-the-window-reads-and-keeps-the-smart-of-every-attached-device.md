# The window reads and keeps the SMART of every attached device

Decision 0044 tells a device alert from the health that the system reports of a device without administrator permission. On Windows that is the storage stack's summary of the disk (`StorageDeviceManagementStatus`, what `Get-PhysicalDisk` shows): it says "Healthy" until the device itself predicts its failure, and says nothing of the counts that tell of a device going bad long before, such as sectors it had to reallocate or cannot read. Those counts are the device's SMART data, which Windows hands to a program only through a handle opened with read and write access to the device, so only with administrator permission (`Get-StorageReliabilityCounter` is refused without it, checked on the owner's computer, 2026-11-10). Decision 0047 already has one program that runs with that permission, on the operator's request: the device identity reader.

## Decision (operator, 2026-11-10)

1. **Whenever the window asks for administrator permission, the reader reads every attached device.** One run of the device identity reader takes every device that the latest read of the attached devices lists (Devices), the one asked for first, under one question of Windows' User Account Control: that of the enclosure question of a FULL verify, Read the device's own serial... of Devices, Register Archive's Record the device's own serial, and the new **Read the SMART of all devices...** at the head of Devices (with a shield), which asks for nothing else. The window and the command line stay unprivileged (R-08, R-12); the command line never starts the reader and shows no SMART.

2. **What the reader sends.** Of each device, side by side (a thread for each, so that sleeping hard disks spin up together):
   - an ATA device, directly or behind a bridge: IDENTIFY DEVICE (`0xEC`), SMART READ DATA and SMART READ THRESHOLDS (`0xB0` with feature `0xD0` and `0xD1`, LBA mid `0x4F`, LBA high `0xC2`, one 512-byte block each), through ATA pass-through, and where IDENTIFY DEVICE fails that way, all three inside ATA PASS-THROUGH (16) (SAT); each command given 15 s;
   - an NVMe device (the storage driver names its bus NVMe): Identify Controller (CNS `0x01`, 4096 bytes) and the SMART / Health Information log (log page `0x02`, 512 bytes), through `IOCTL_STORAGE_QUERY_PROPERTY` with `StorageAdapterProtocolSpecificProperty` and `StorageDeviceProtocolSpecificProperty`.

   Every command only returns what the device says of itself: no self-test is started, nothing is turned on or off, nothing of the content is read and nothing is written. Its arguments are now the result file first, then one to 64 device numbers, each once (`veriarchive-device-identity.exe <result file> <device number>...`); it refuses anything else as before, and writes `{"devices": [...]}`, for each device in the order given the pages it read in lowercase hex and how (`ata`, `sat`, `nvme`), or why nothing (`open-failed`, `not-passed` with the Win32 error), and where the identification came back but SMART did not, why (`smart_error`). It decodes nothing but what tells whether IDENTIFY DEVICE came back. The window waits for it at most 120 s (60 s before), reads at most 1 MiB of result (4 KiB before), and binds each device to the description it had before Windows asked, as decision 0047 binds one.

3. **The window decodes, unprivileged.** The device's own identity (model, serial, firmware, WWN) from the identification it returned (ATA words, or NVMe bytes 4-71), the ATA attributes with their thresholds, and the NVMe health log, by plain C++ that the unit tests check on every system (`src/core/smart/`). A page whose checksum does not hold is not decoded. Where the identification came back and SMART did not, the read says why, from the identification where it tells: SMART not supported, SMART turned off, no answer in time, or the enclosure does not pass SMART commands on.

4. **Every read is recorded in the repository, outside the hash chain.** Schema version 4 adds `smart_reads (id, read_at, seen_json, model, serial, wwn, firmware, how, identify, data, thresholds, problem, detail)`: one row for each device read, a read that gave nothing included (with why), the device as the system described it without elevation (`seen_json`, as media evidence keeps a device), its own identity, and the pages as BLOBs as the device returned them, so that a better decoding reads old reads anew. SMART tells of a device, not of an archive's content: it is no run, no media evidence, and not in `verify_runs`' chain (R-90). `repo rebuild-index` keeps it, as it rebuilds only the index. A repository of version 1, 2 or 3 is raised to 4 when this version opens it, after a copy of its database is kept (decision 0032); 1.2.1 and earlier versions refuse it from then on.

5. **What a read says.** A **SMART alert** (a device alert, GLOSSARY) where:
   - an ATA attribute's value is at or below its threshold (a threshold of 1 to 253);
   - a raw count above zero of reallocated sectors (5), pending sectors (197), offline uncorrectable sectors (198) or reported uncorrectable errors (187);
   - NVMe: a critical warning, the available spare below its threshold, media and data integrity errors above zero.

   Hints, which alert nothing: UltraDMA CRC errors (199) that rose since the read before (a cable or an enclosure that loses data on the way, rarely the device), and a count of pending or offline uncorrectable sectors back at zero ("cleared (8 → 0)", once). Temperature, power-on hours and the other values are shown, never judged.

6. **Judged by the latest read, compared with the one before.** The device's latest read that gave data decides, compared with the read before it of the same device (by its own serial, or WWN; behind another enclosure too): "increased (0 → 8)", "8 (as in the last read)", "3 (8 in the last read)". An alert stays as long as its count stays above zero, as reallocated sectors do for good, whether it rose or not (operator: "好"); a count that comes back to zero alerts no more (operator: "如果修復了 像是 C5 變成0 可修復的就變成健康"). Pending sectors that went back to zero because the device reallocated them raise the count of reallocated sectors, which then alerts.

7. **Devices** shows, where this computer has a reader, a box at its head: when SMART was last read and how many attached devices alert, Read the SMART of all devices..., a spinner while it reads, and what it does (User Account Control asks; model, serial and SMART of every attached device, nothing of their content, nothing changed; a sleeping disk spins up; also whenever a device's own serial is read; recorded and compared with the last read of the same device). Each device's card has a SMART pill beside its health ("SMART alert", "SMART OK", "SMART cannot be read", "SMART not read") and a SMART section: when and how it was read ("through its enclosure (SAT)", "directly (ATA)", "NVMe health log"), its alerts in red with the advice to copy the archives on it to another device soon and verify the copies, its hints, why its latest read gave nothing, the values most looked at, and, folded, every attribute (ID, attribute, current, worst, threshold, raw) or NVMe value, and its reads newest first (5, 197, 198, 199 and temperature, or the NVMe ones). A device is found among the reads by what the system tells of it without elevation (model, serial and WWN as reported, capacity), never by a read made behind an enclosure that hid the identity of the device inside (point 11). A read toast says how many devices were read and how many alert, or why none was (permission declined, no reader).

8. **Archives** marks an archive whose carrier's device (as recorded, and where the latest read of the attached devices finds the archive, as point 11 finds its reads) has a latest SMART read that alerts: "⚠ SMART: Pending sectors increased (0 → 8)" beside its result, "(+1)" for each further alert, its row's dot red, its details' alert line ("SMART of its device, read ...: ...; Devices shows all of it."), and it counts under the overview's Device alert and in "need attention" (operator: question 1, "好"). It is the window's alone: `archive_statuses` never fills it (`ArchiveStatus::smart_alert`), so `archive list` and the rest of the command line are as before.

9. **Linux is not changed**: decision 0044's udisks2 health stays, the window has no reader there, and shows no SMART box; a repository that holds reads made on Windows shows them where a device is described alike.

10. **The version is 1.3.0**, as the schema changes.

11. **Behind an enclosure that hides the device's identity, nothing is shown until the device is read again** (operator, 2026-11-10: "外接盒如果沒有管理權限重新讀就不顯示健康狀態"). All that the system tells of such a device is its enclosure's, so another device put into the same enclosure since, or behind a bridge that reports one serial for every device, looks alike. Its card shows "SMART to read again" (SMART 需重新讀取, neutral) and why ("This enclosure does not tell which device is inside, so no SMART read before is shown: Read the SMART of all devices... reads it again."), and no read, until the window keeps a read of its own identity (decision 0047's kept read: made with administrator permission while the window watches the device, dropped once it is detached, changed, or not watched for a while). Then its reads are those of that device, found by its own serial or WWN, behind any enclosure. A read made behind such an enclosure is never found by the enclosure's description alone, also not for an archive's carrier as recorded: Archives marks such an archive only while the device is attached and read again. Devices whose identity nothing hides are found by their description, as point 7 says.

12. **A FULL verification may record the SMART read as it starts** (operator, 2026-11-11: an option, off by default). Settings has, where this computer has a reader, **Read SMART when a FULL verification starts** (the config file's `read_smart_with_full_verify`, written only where it is on), saying that Windows asks for administrator permission each time. On, every FULL verification started in the window (FULL verify and its variants, Confirm and FULL verify..., Verify a folder or volume..., Verify the attached archives that need it, which reads once for all of them) first reads the SMART of every attached device, as point 1 does, after Windows asked; the reads of a run of the reader that ended less than 5 minutes before serve instead, with no second question (as after the enclosure question). The verification then starts, and records the reads of the devices of the volume it reads (found by the system's name for the device and its description at that moment) in its counts, the member `smart` (`read_at`, `seen`, `device`, `firmware`, `how`, the pages `data` and `thresholds` in hex, `problem`), hash-chained with the run whatever its result, and in its record `run:<run_id>`, which a resume records again and reads nothing new. Declined, failed, or with another read waiting, the verifications start without SMART, and a toast says why. A resume reads nothing. The run's result page lists each read beside the devices ("SMART OK · read ..., through its enclosure (SAT)", "SMART alert: ...") and a read that alerts among its device alerts, so does its verification report; a run compares its read with none. The command line never reads SMART: `VerifyRequest::smart_reads` is filled by the window alone, and a run it records holds none.

### Deliberate departures from the approved design

1. **"Read the SMART of all devices..." (讀取所有裝置的 SMART…)**, where the owner proposed and the prototype showed 讀取所有硬碟的 SMART…: GLOSSARY names a device 裝置 and rejects drive and disk (硬碟) as its synonyms (project rule 11), and the page it stands on is 裝置, whose devices include SSDs and NVMe devices, which are no 硬碟. Recommended to the owner (2026-11-10), who asked for advice; their choice is still to come.
2. **A picture of its own** (`12-smart.png`): the screenshot tour presses Read the device's own serial... as before, which now reads every sample device's SMART too (the sample reader answers with made-up pages: `SAMPLE-DEVICE-02`, which reports a warning, has 8 reallocated and 8 pending sectors), and pictures the card of that device. `10-devices.png` is taken before the read, as before, and shows `SAMPLE-DEVICE-03`, behind its sample enclosure that hides the device's serial, with SMART to read again.

### Not built

1. **USB bridges for NVMe devices** (JMicron JMS583, Realtek RTL9210 and the like) take vendor commands, not SAT: their devices read as "The enclosure passes no ATA command on to the device."
2. **SCSI and SAS devices' own SMART** (log pages, `LOG SENSE`): a SAS device behind a controller that does not translate SAT is read so too.
3. **No SMART on the command line**, no `--json` of it, no SMART in a notification, the history's marks or Archives' marks of a run: a run records its devices' SMART only where point 12 read it, and Archives judges by the latest read, never by a run's.

### Open questions for the owner

2. **The enclosure question now waits for every attached device** (up to 120 s where a sleeping disk spins up), where it waited for one, as point 1 reads every attached device whenever the window asks for administrator permission. Keep it so, or have the question read only its device, and leave the others to Read the SMART of all devices...?

## Why

The owner keeps archives on data disks, verifies them FULL for 10 to 16 hours, and asked how VeriArchive measures a disk's health (2026-11-10). It does not, beyond what Windows says without elevation, which says nothing until the device predicts its failure. The counts that tell earlier are the device's SMART, which Windows gives only with administrator permission, and VeriArchive already has one elevated program, started on the operator's request through Windows' own question, which reads only what a device says of itself and changes nothing (decision 0047): reading SMART is two more such commands, and NVMe's log one more. Reading every attached device in the run that asks anyway costs no further question. Keeping the pages, not only what was made of them, lets a comparison with the read before tell "increased" from "as before", and lets a later version decode old reads anew. They are kept outside the history's chain: SMART is no evidence of an archive's content, and the chain covers runs alone.

The alert criteria are those that tools like smartctl and CrystalDiskInfo use, which the owner agreed to: counts that mean the device found sectors it cannot read, or values at their maker's threshold. CRC errors mean data damaged on the cable or in the bridge, which the device itself corrected by asking again, so they are a hint about the connection. Temperature depends on the room and the load.

Rejected alternatives:

- Asking Windows each time Devices reads (every 30 s): a question of Windows every read; R-12.
- A service or a helper that stays running with administrator permission: decision 0039.
- WMI (`MSStorageDriver_FailurePredictData`): administrator permission too, ATA only, nothing through most bridges, and nothing of NVMe.
- Recording every SMART read in a run's counts: a run reads one archive's devices, SMART tells of every device at once, and a read on Devices belongs to no run; a run records only the read made as it was started, where the operator chose it (point 12).
- Asking Windows at every FULL verification by default: a verification is often started and left for hours, and the question would wait; it is the operator's choice in Settings (point 12).
- Keeping only decoded values: an earlier decoding's mistake would stay in the record.
