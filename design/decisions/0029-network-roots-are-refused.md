# A root on a network share is refused before anything is read

An archive is a file tree on exactly one volume (R-30), known by that volume's filesystem id and its devices (§B10). A network share is no volume of this computer: neither the filesystem id nor the devices behind it can be read here. On Windows a root on a share, a network path (`\\server\share\Photos`) or a folder on a drive letter mapped to a share, failed when its volume was looked up, with "cannot identify the volume of the root: GetVolumeNameForVolumeMountPointW failed (Win32 error 87)", which does not say why. A root written in the `\\?\` or `\\.\` form with a drive letter (`\\?\D:\Photos`, `\\.\D:\Photos`) failed with "the root is not on the reported volume": the C++ library (MinGW's `lexically_relative`) takes the `D:` inside that form for a root name of its own, so the root is not found below the mount point of its volume. A root on a volume's GUID path (`\\?\Volume{...}\Photos`, the name `mountvol` lists for a volume) did not fail: it was registered and verified, as the same archive as the folder through the volume's drive letter (the same volume and `root_subpath`). Only the volume's root folder itself, `\\?\Volume{...}\`, failed on the command line: the user interfaces dropped its last separator, which left the name of the volume itself, and `register` and `archive relocate` stopped with "not a directory", as the C++ library (`std::filesystem::is_directory`) cannot tell that a volume's GUID path is a folder. For a volume that has no drive letter and no folder path, it is the only name: verification by archive uuid never finds an archive there, as it looks only among volumes that have a mount point (`IMediaEnumerator::volumes`), so such an archive was verified by its GUID path alone. On Linux a root on a network filesystem (NFS, SMB, sshfs), or on a share that GNOME or KDE opened (GVFS, kio-fuse), was taken: it was described as a volume without a device, identified only by the kernel's filesystem id, which NFS and FUSE report as zero for every share. Such shares then read as the same volume, and their identity proved nothing.

## Decision

1. **Where a root is taken.** `register`, `verify --full <root_path>` (also with `--resume`) and `archive relocate` on the command line; Register Archive and Verify Archive in the GUI. The root made from what the operator typed (decision 0027, `app::typed_root`) is judged before anything of it is read: before its volume is looked up, the repository is written, or a scan starts. A refused root ends the command with exit 10 (usage), as a root that is not a folder does; the GUI shows "Not registered: ..." or "Not verified: ...". Verification by archive uuid takes no root: it looks for the archive's carrier among the volumes, now also those that have no drive letter or folder path (point 3), and the root it finds there is judged by none of these rules, which are for a root the operator gives.
2. **A root on a network share** is refused with "the archive root is on a network share; VeriArchive registers and verifies folders on volumes attached to this computer".
   - Windows: a network path (`\\server\share\...`, `//server/share`); a path in the `\\?\` or `\\.\` form that names a share (`\\?\UNC\server\share`, in any case) or a network drive; a path from the root of a drive letter that Windows reports as a network drive (`GetDriveTypeW`: `DRIVE_REMOTE`). A drive letter made with subst for a folder on a share is resolved to the share first (decision 0027), so it is refused the same way. A network path is told from its text alone: nothing on the share is opened, so a share that does not answer is refused at once.
   - Linux: a root on a network or remote filesystem, told by the filesystem type that `statfs` reports, then by the type of the mount that contains the root in `/proc/self/mountinfo`: the types the repository's own check knows (R-83 step 4), such as `nfs`, `nfs4`, `cifs`, `smb3`, `9p` and FUSE's `sshfs` or `rclone`, and the FUSE mounts through which GNOME and KDE give other programs the shares they opened (SMB, SFTP, WebDAV, ...): GVFS's one mount `/run/user/<uid>/gvfs` (`fuse.gvfsd-fuse`), whose folders GNOME Files and the GTK file dialog (the GUI's **Choose...**) give for a share, and KDE's `kio-fuse`. GVFS also shows phones and cameras there (MTP, PTP); they are no volume of this computer either, and are refused in the same words. A local volume mounted in a folder of a share is not on the share.
3. **A root written in the `\\?\` or `\\.\` form** (Windows), when it names no share, is refused with "write the archive root without \\?\ in front (for example D:\Photos)", naming the prefix as typed. The form passes a path to Windows without the changes Windows makes to other paths, and with a drive letter the volume lookup and the C++ library misread it. **A volume's GUID path is taken** (operator, 2026-10-16), as it was before this decision: `\\?\Volume{...}\` as `mountvol` lists it ("Volume" in any case, the GUID's 32 hexadecimal digits and 4 dashes between braces), with either separator, also without its last separator, and a folder below it (`\\?\Volume{...}\Photos`). It is the only name of a volume that has no drive letter or folder path, and through it a folder is the same archive as through the volume's drive letter or folder path (the same volume and `root_subpath`), for `register`, `verify --full <root_path>` and `archive relocate`, on the command line and in the GUI. A volume's GUID written otherwise, in the `\\.\` form (`\\.\Volume{...}\`) or with its GUID cut short, stays refused, with "write a volume's GUID path exactly as mountvol lists it, with \\?\ in front". Taking the path takes four more things:
   - What follows its GUID is made normal as the user interfaces make any other root typed (`app::typed_path`, through `platform::normal_volume_guid_path`, which is `windows::normal_volume_guid_path`, plain C++, on Windows): every run of separators one `\`, `.` dropped and `..` dropping the name before it, never the volume's root folder, and its prefix written `\\?\`. So `\\?\Volume{...}\Photos\..\Music` is the root `\\?\Volume{...}\Music`, as `D:\Photos\..\Music` is `D:\Music`, and `//?/Volume{...}/Music/` is that root too. "Volume" and the GUID keep the case they are written in, which Windows does not tell apart. Windows reads a path in the `\\?\` form exactly as given, while the root's place on its volume (`root_subpath`) is told from the path made normal: as typed, the root was identified as its archive and then read verbatim, so a verification recorded `FAILED` for an intact archive (`FilesystemAccessError`, Win32 error 123) and `register` said "not a directory" of a folder that exists.
   - The root folder of the volume keeps its separator, `\\?\Volume{...}\`, as `D:\` keeps its own (`without_trailing_separators`; `\\?\Volume{...}\\` is that root too): without it, the path names the volume itself, which Windows does not take for a folder. Written without it, `\\?\Volume{...}` is taken as typed.
   - Whether a root is a folder (`register`, `archive relocate`, and Resume on a stopped registration in the Archive List, decision 0022) is asked of Windows (`platform::is_directory`: `GetFileAttributesW` in the `\\?\` form, R-23, and once more with the separator for a GUID path written without it) rather than of the C++ library, whose `std::filesystem::is_directory` fails on a volume's root folder named by its GUID path.
   - On Windows, `IMediaEnumerator::volumes` lists a volume that has no drive letter or folder path as well, with its GUID path as its mount point (`windows::volumes_to_list`), where it left such a volume out. So `media list` shows it, and verification by archive uuid finds an archive on it, at a root VeriArchive finds itself (`\\?\Volume{...}\`, `\\?\Volume{...}\Photos`), which no rule of this decision judges (point 1): it is read, recorded with the run (decision 0022), and found again by the archive's uuid when the run is resumed (`verify --full <archive_uuid> --resume <run_id>`, Resume in the Archive List).
4. **A root whose filesystem cannot be told** (on Linux, `statfs` fails or no mount contains the root) is not refused here: its volume lookup then says what is wrong, as before. The repository's check fails closed instead (R-83 step 4): SQLite must never be placed on a share unawares, while an archive root that cannot be told is still looked up as a volume, which then fails or identifies it.
5. **Platform.** `platform::archive_root_kind(root)` tells `Usable`, `NetworkShare` or `DevicePath`. Windows: `windows::root_kind`, plain C++ over the root's text and a question about its drive letter, which the platform answers with `GetDriveTypeW`; a volume's GUID path in the `\\?\` form is `Usable` (point 3). Linux: `linux_mounts::archive_root_on_network`, plain C++ over the type that `statfs` reports and the parsed mountinfo; the repository's check asks `linux_mounts::repository_on_network`, which tells the same way and fails closed (point 4). The platform itself only reads: `statfs`, the root made canonical, and `/proc/self/mountinfo`. `app::root_refusal(root)` gives the refusal's words, which both user interfaces show; it is asked in the GUI on the operation's own thread, as on Linux it reads the root's filesystem. `platform::is_directory(path)` tells a folder, on Windows by `GetFileAttributesW`, on Linux by `std::filesystem::is_directory`; `app::root_not_taken(root, typed)` asks it after `root_refusal`, for the command line's `register` and `archive relocate` and the Archive List's Resume of a registration. `windows::volumes_to_list`, plain C++ over the names that `FindFirstVolumeW` and `GetVolumePathNamesForVolumeNameW` give, chooses the mount point a volume is listed under (point 3). `platform::normal_volume_guid_path(path)` makes a volume's GUID path normal after its GUID (point 3): on Windows `windows::normal_volume_guid_path`, plain C++ over the path's text, which tells the GUID as `root_kind` does (`windows::names_volume_guid`) and makes what follows it normal as `long_path` makes what follows a drive letter; on Linux it gives every path unchanged. `app::typed_path` asks it of a path that starts with two separators, and keeps any other such path as typed.
6. **A root that holds the repository** (operator, 2026-10-27). A registration (`register`, also with `--resume` or `--lost-manifest`, and Register Archive, also its resume from the Archive List) refuses a root that holds RepositoryRoot, or lies inside it, before anything of it is read, as soon as the repository is known, with exit 10 (`RegisterFailure::Kind::Invalid`): "this folder or volume holds VeriArchive's repository R, which changes while it is read, so a verification of this archive could never pass; register a folder that does not hold the repository, or move the repository out of it first", and "this folder lies inside VeriArchive's repository R, ...; register a folder outside the repository". The repository changes while such a root is read and at every operation after (its database and journal, its new manifests), so the archive's verifications would always find entries modified or new: a portable program folder unzipped on a data disk and the disk registered whole gave an archive that never passed. Leaving the repository out of the scan automatically was the other way; the operator chose to refuse in V1, as an exclusion that is not in the manifest's list (R-54) would change what a manifest holds and how it is checked. The roots are compared by their text (`path_within`): element by element after `lexically_normal()`, case-insensitively as roots on one volume are (decision 0001), the root as the user interfaces make it (a drive letter made with subst resolved, decision 0027), the repository as it was resolved (§B7.4). Verification and relocation do not refuse such a root: an archive that holds the repository, registered before this decision, verifies as it always did, and fails.

## Why

A share is no volume. VeriArchive tells which media holds an archive by the filesystem id and the devices of its volume (§B1.2, §B10), and a share shows neither to this computer: on Windows nothing can be read, and on Linux the stand-in id is the same for every share, so a verification would accept any share at that path as the archive's carrier. The operator's archives lie on data disks attached to this computer (§A1: V1 targets data disks).

The roots are refused where they are taken. The user interfaces already make the root there from what the operator typed (decision 0027), and the platform knows the drive types and the mounts, so the operator learns at once what is wrong with the root typed, before anything is read or written, in words of its own. The engines receive only roots that can be looked up, and their volume lookup (`IMediaEnumerator::volume_for_path`, §B9) is unchanged.

The `\\?\` form is refused rather than taken apart: the form is for programs that pass a path to Windows unchanged, and a root written by a person has a usual form, which the message shows. A volume's GUID path is the exception (operator, 2026-10-16): Windows has no other name for a volume that has no drive letter or folder path, and no drive letter could stand in for it. This decision first refused it with the rest of the form, one rule for the prefix, taking it to fail as the drive-letter forms do; it did not (see the context). Refused, a folder on such a volume could be neither registered nor verified until the volume was given a drive letter, and an archive that an earlier version registered there not at all. Its `\\.\` form, which Windows also reads, is not taken: one spelling per root keeps one root in a registration's plan, which `register --resume` finds by its root, and the `\\?\` form is the one `mountvol` lists.

The volume's root folder keeps its separator for the same reason as `D:\` keeps its own: without it the path names something else, here the volume itself, which Windows takes for no folder, so no check that the root is a folder could pass. That check asks Windows, as the platform's reads do (R-23), because the C++ library's `std::filesystem::is_directory` answers wrongly for that root, which is a folder. And verification by archive uuid, which looked only among the volumes that have a mount point, now finds a volume that has none under its GUID path, as the root of an archive on it may be written: the operator asked that a root VeriArchive finds there itself is never refused, and it is not, as the rules above judge only what the operator gives.

A GUID path is made normal after its GUID because the root identified must be the root read. The place of a root on its volume is told from the path made normal (`root_subpath_of`, as for every root), while Windows reads a path in the `\\?\` form as given, `..` and `.` as names: a root through `..` was the archive by its identity and a folder that does not exist where it was read. Any other root typed is made normal where it is typed (`app::typed_path`), so `D:\Photos\..\Music` is `D:\Music`; the GUID path, taken as a root like the others, is made so in the same place, and one folder keeps one spelling, as its root_hint, the root in a registration's plan and in a run's record. The prefix is written `\\?\` for the same reason, as `mountvol` lists it.

Rejected alternatives:

- Registering a share by what the server tells (its name, the share's name): it names a place, not media; other media behind the same name would read as the same archive, and nothing would tell a copy from the original.
- Refusing in the volume lookup of each platform (`volume_for_path` failing with these words): the refusal would come after the repository is opened and read, wrapped as "cannot identify the volume of the root: ...", with the exit code of a failed lookup; and on Linux the lookup would have to refuse what it describes today for every caller.
- Taking `\\?\D:\Photos` as `D:\Photos`: one more way of writing a root to keep apart from the others (the root in a registration's plan, `register --resume` finding it), for a form people do not type, and one that names a volume's GUID path has nothing to be taken as.
- Failing closed for archive roots too (refusing a root whose filesystem cannot be told): the volume lookup says more about such a root than "network share" would.
- Refusing a volume's GUID path still, so that the volume is given a drive letter or folder path first, as this decision first did: the operator chose to take it again. A volume that should keep no letter (one of many on a device, or one whose letter is wanted elsewhere) would stay out of reach, and an archive registered through the path by an earlier version could be verified only after the volume was given a letter or folder path.
- Taking the `\\.\` form of a GUID path as well: a second spelling of the same root, whose plan `register --resume` would not find by the other; `mountvol` lists the `\\?\` form.
- Dropping the last separator of a volume's root folder named by its GUID path, as of any folder (`\\?\Volume{...}`), as the user interfaces did until now: that path names the volume, which Windows takes for no folder.
- Asking the C++ library whether a root is a folder, with an exception for a volume's GUID path: the platform knows how Windows reads its paths (R-23), and the library's answer for that root is wrong, not missing.
- Taking a GUID path as typed, `..`, `.` and separators in a row included, as this point first did: the root was identified by its path made normal and read as typed, so an intact archive failed its verification, which the history kept, and `register` refused a folder that exists.
- Refusing a GUID path with `.`, `..` or separators in a row after its GUID (exit 10, in words of its own): a root through a drive letter is taken so, made normal, and the operator would be asked to resolve by hand what VeriArchive resolves for any other root.
- Making the path normal only where Windows is asked (`long_path`): the root would be read right, but its root_hint, the root of a registration's plan and of a run's record would keep the spelling typed, two spellings for one folder.
- Leaving verification by archive uuid to the volumes that have a mount point, so that an archive on a volume without one is verified by its GUID path alone: it would read as "not on any attached volume" while its device is attached, also in a resume by the archive's uuid, as the Archive List's Resume makes it (decision 0022).
- Listing the volumes without a mount point only where verification by uuid looks for an archive, not in `media list`: `media list` shows what `IMediaEnumerator::volumes` gives, one list of the volumes of this computer.

## Consequences

- Windows: the roots that failed before are refused, now before anything is read, with the reason named, and with exit 10 instead of 11: a network path, a folder on a drive letter mapped to a share, and the `\\?\` and `\\.\` forms of a drive letter. A volume's GUID path is taken, as before this decision, and now also as the volume's root folder on the command line, where `register` and `archive relocate` stopped with "not a directory". A folder on a volume that has no drive letter or folder path is registered, verified (by its root and by its archive's uuid) and relocated to through the volume's GUID path, without a drive letter given to the volume first; an archive that an earlier version registered so is verified again. An unfinished registration through a GUID path is resumed by `register --resume` and by Resume in the Archive List; an interrupted verification or relocation through one continues as any, as their resumes look at the volume and the folder, not at the path written. A volume's GUID written in the `\\.\` form, or with its GUID cut short, is refused (exit 10), saying how to write it. A GUID path written with `.`, `..` or separators in a row after its GUID, which was identified as its archive and then read as written (a verification recorded `FAILED` for an intact archive, and `register` said "not a directory" of a folder that exists), names the folder they resolve to, which is read and recorded; a prefix written `//?/` is recorded `\\?\`.
- Linux: a root on a network filesystem, or on a share that GNOME or KDE opened, which was registered, verified and relocated to until now, is refused. An archive registered on one by an earlier version can no longer be verified by its root; verification by its uuid looks for it among the volumes, where Linux still lists a network filesystem as a volume without a device (`media list`), and finds it as before. An unfinished registration or relocation of such a root cannot be resumed, only abandoned (decisions 0025, 0026).
- `media list` on Windows lists a volume that has no drive letter or folder path too (a recovery partition, say), under its GUID path, where it left it out; on Linux it is unchanged. So is the repository's check (R-83 step 4, `allow_network_repository`), except that it knows the same types and so counts GVFS's and kio-fuse's mounts among the network filesystems too: a repository on a share that GNOME or KDE opened is refused unless `allow_network_repository` is set, as one on an SMB mount always was.
- The Archive List shows no approximate total for a whole volume registered through its GUID path until the scan has counted its files (decision 0022, point 3): the C++ library cannot read the space in use through that path (`std::filesystem::space`).
- Decision 0022 names a directory listing on "a network share" among the reasons why an operation may give no progress for minutes: a share is no longer an archive root; a failing device still is.
- No change to the manifests, the database or the golden test.
- Tests: the classification as plain functions on both systems: Windows (network paths with either separator, `\\?\UNC\` and `\\.\UNC\` in any case, a drive letter mapped to a share also behind `\\?\`, the `\\?\` and `\\.\` forms of a local volume's drive letter, a local volume's drive letter, paths that name no drive letter, a name that only starts with UNC, and no question asked for a network path); Linux (sample mountinfo with NFS, SMB and sshfs mounts, a local volume mounted in a folder of the NFS share, ntfs-3g on a local volume, the FUSE mounts of GVFS and kio-fuse below the user's runtime folder, a tmpfs that is not refused, a path that only starts like the share's mount point, and no mount at all; NFS, SMB and the other network filesystems by the type that `statfs` reports, whatever the mounts say, sshfs by its mount where `statfs` reports FUSE, a local root and ntfs-3g not refused, and where neither tells, `statfs` having failed or no mount containing the path, the repository's check failing closed and an archive root not refused); the refusal's words in both languages, a local folder never refused, and on Linux the same text taken as a name; the CLI end to end on Windows: `register`, `verify --full` and `archive relocate` with a sample network path, and `register` and `verify --full` with the `\\?\` form, each exit 10 in either language and `--json`, nothing recorded. A mutation check removed each guard in turn (a network path, a share behind `\\?\UNC`, a network drive behind `\\?\`, `UNC` in any case, a name that only starts with `UNC`, a network drive, the `\\?\` form, the `\\.\` form, on Linux the mount's type, GVFS's and kio-fuse's types, a path that no mount contains, the type that `statfs` reports and each network filesystem's magic number in it, the mounts asked after it, nothing told where `statfs` failed, the repository's check failing closed and an archive root's not, the refusal in `register`, `verify` and `archive relocate`, the prefix named as typed, the words of each refusal), and each removal failed the test meant for it.
